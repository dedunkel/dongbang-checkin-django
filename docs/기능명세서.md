# 동방배틀 체크인 시스템 — 기능명세서

설치·배포·운영 순서는 [README.md](../README.md)를 참고하세요. 이 문서는
"무엇을 할 수 있는가"를 화면/역할/데이터 단위로 정리한 기능 스펙입니다.

## 1. 개요

- **목적**: 댄스 배틀 행사("동방배틀")의 참가 신청 접수(구글 폼) 이후 —
  검수 → 라벨/QR 발급 → 현장 체크인 → 점수 시트 반영까지의 운영 과정을
  하나의 시스템으로 처리한다.
- **범위**: 신청 접수 자체는 기존 구글 폼을 그대로 쓰고, 이 시스템은 그
  이후(검수~체크인~정산)를 담당한다. 학적증명서 OCR 자동 대조, 문자/카카오
  알림톡 자동 발송은 범위 밖이다(§7 참고).
- **회차(Event) 단위 운영**: 모든 데이터는 회차에 종속되며, 신규 신청을
  받는 "활성 회차"는 항상 하나뿐이다(하나를 활성화하면 나머지는 자동
  비활성화).

## 2. 사용자 역할 및 권한

| 역할 | 로그인 | 접근 가능 범위 |
| --- | --- | --- |
| 방문자(참가자/관람객) | 불필요 | 홈, 예비 신청 폼(`/register/`), 본인 QR 확인(`/qr/<token>/`), QR 스캔 시 뜨는 공개 확인 팝업(`/checkin/scan/<token>/`) — 정보 열람만 가능, 체크인 확정은 불가 |
| 스태프 | 필요 (`is_staff`) | 현장 체크인 스캐너(`/checkin/`)만. 회차·참가자 관리 화면(Django Admin)에는 들어갈 수 없음 |
| 운영진 | 필요 (`is_staff` + "운영진" 그룹) | 스태프 권한 전부 + 회차·참가자 관리 전체(Django Admin: Events, Participants) + 마스킹 없는 민감 정보 다운로드(QR 발송용 명단, 점수표, CSV 백업 — `checkin.export_sensitive_data` 권한) |
| 슈퍼유저 | 필요 (`is_superuser`) | 운영진 권한 전부 + 계정 관리 화면(`/admin/accounts/`)에서 스태프·운영진 계정 초대/권한 변경/비밀번호 재설정 메일 발송/계정 삭제 |

권한은 `is_staff`/`is_superuser`/"운영진" 그룹 조합으로 표현되며, 계정
관리 화면에서는 이 조합을 "스태프/운영진/슈퍼유저" 3단계 라디오 선택
하나로 단순화해 보여준다(`checkin/auth_admin.py`).

## 3. 데이터 모델

### 3.1 Event (회차)

| 필드 | 설명 |
| --- | --- |
| `volume` | 회차 번호 (고유, 예: 33) |
| `name` | 회차 이름 (예: "동방배틀 vol.33") |
| `event_date` / `location` | 행사 날짜/장소 (선택) |
| `is_active` | 신규 신청을 받는 현재 회차인지. **동시에 하나만 true** — 저장 시 자동으로 나머지가 false로 바뀐다 |
| `sheet_sync_url` | 이 회차의 점수 시트 SheetSync.gs 웹 앱 URL (선택, §5.3) |

### 3.2 Participant (참가자/관람객)

| 필드 | 설명 |
| --- | --- |
| `event` | 소속 회차 |
| `entry_type` | `참가` / `관람` |
| `name`, `phone`, `school`, `academic_status` | 구글 폼 신청 정보. `name`은 "본명/댄서명" 형식(구분자 앞뒤 공백은 무시하고 파싱, `split_display_name`) |
| `genre` | 참가자만 사용. 왁킹/팝핑/락킹/하우스/크럼프/힙합/브레이킹 중 하나(신청자당 장르 1개만 지원) |
| `payer_name` | 입금자명 (입금 내역 대조용, 참고 정보) |
| `external_ref` | 구글 폼 시트 행에 대응하는 참조값. 같은 회차에서 중복 수집 방지에 사용 |
| `verification_status` | `PENDING`/`APPROVED`/`REJECTED`/`N_A`(관람은 해당없음) — 학적검수 상태 |
| `verification_note` | 학적검수 관련 자유 메모(선택). 반려 사유 등 운영진 참고용이며 참가자에게는 노출되지 않는다 |
| `payment_status` | `PENDING`/`PAID`/`REFUND` — 입금 상태 |
| `label_group`, `label_number`, `label_code` | 라벨(조/번호). `label_code`(`"A-3"` 형식)는 항상 group/number로부터 자동 계산되며 직접 수정해도 무시된다 |
| `qr_token`, `qr_sent_at` | 개인 QR 식별 토큰과 발급 시각 |
| `checkin_status`, `checked_in_at` | `NOT_CHECKED_IN`/`CHECKED_IN`과 체크인 확정 시각 |

### 3.3 데이터 제약

- 같은 회차·장르 안에서 같은 (group, number) 라벨 슬롯은 중복 배정될 수
  없다 (`label_slot_unique`, DB 레벨 제약).
- 같은 회차 안에서 같은 `external_ref`로 중복 생성될 수 없다
  (`participant_external_ref_unique`) — 구글 폼 재수집이 멱등하게 동작하는
  근거.
- 회차를 삭제하면 그 회차의 참가자도 함께 삭제된다(연쇄 삭제) — CSV 백업
  없이 삭제하면 복구 불가.

## 4. 기능 명세

### 4.1 공개 페이지 (로그인 불필요)

| 화면 | 경로 | 설명 |
| --- | --- | --- |
| 홈 | `/` | 활성 회차 안내 |
| 예비 신청 폼 | `/register/` | 구글 폼을 안 쓸 경우를 위한 대체 신청 경로. 활성 회차가 없으면 신청 불가 안내만 표시 |
| 개인 QR 확인 | `/qr/<token>/` | 본인 QR 코드(PNG, 서버에서 생성) 표시. 스캔 시 실제로 열리는 링크(`/checkin/scan/<token>/`)를 인코딩 |
| QR 스캔 확인 팝업 | `/checkin/scan/<token>/` | 아무 QR 리더로 스캔해도 열리는 참가자 정보 확인 화면. **정보 열람만 가능** — 실제 체크인 확정은 스태프 로그인이 있어야 하는 별도 POST(`scan_confirm`)로만 이뤄진다 (본인/제3자가 QR을 먼저 열어봐도 체크인되지 않도록 하는 설계) |

### 4.2 스태프 기능

| 기능 | 위치 | 설명 |
| --- | --- | --- |
| 현장 체크인 스캐너 | `/checkin/` (`@staff_member_required`) | 카메라로 QR 자동 스캔 → 조회 후 라벨 코드/이름/장르 표시 → 체크인 확정. 이미 체크인된 QR은 "이미 체크인됨" 표시(중복 체크인 방지) |
| 이름/전화번호 수동 검색 | 같은 화면 | QR을 못 보여주는 참가자를 이름/연락처로 검색해 수동 체크인 |

**현장 학적 검수 흐름**: 구분이 참가이고 학적검수가 승인되지 않은 사람(대기·반려)은 QR 스캔 카드, 수동 검색
목록, QR 확인 페이지에서 "학적 검수 필요"로 표시되고 **"검수 완료" 버튼이 먼저** 나옵니다. 검수를 마치면
그다음에 **"체크인 완료" 버튼**이 나옵니다(검수 직후 0.6초는 눌리지 않게 잠금). 이미 검수된 참가자와
관람객은 체크인 버튼만 보입니다.

- "검수 완료"는 학적검수 승인 권한(`checkin.approve_verification`)이 있는 스태프만 누를 수 있습니다.
  권한이 없으면 안내만 보이고 체크인은 할 수 없습니다(권한이 있는 운영진에게 검수 요청).
- 서버도 같은 조건으로 체크인 요청을 거절합니다(화면 우회 방지).
- 반려된 참가자도 같은 "학적 검수 필요"로 보이며 반려 사유는 보여주지 않습니다.
- QR 확인 페이지의 검수 안내/버튼은 로그인한 스태프에게만 보입니다(로그인 없이 열리는 페이지라 검수 여부를 숨김).
- 참가자 본인의 QR 화면(`/qr/<token>/`)에는 검수가 끝나지 않은 참가자에게 "현장에서 학적 확인 서류를 준비해달라"는 안내가 뜹니다.

체크인이 확정되면 백그라운드로 점수 시트에 "도착 여부"가 실시간 반영된다
(§5.3, 실패해도 체크인 자체는 막지 않음).

### 4.3 운영진 기능 — 회차 관리 (Django Admin `Events`)

- 회차 생성/수정/삭제, 활성 회차 전환.
- 목록 액션(선택한 회차 대상, 한 번에 하나씩만 적용):

  | 액션 | 권한 | 설명 |
  | --- | --- | --- |
  | 라벨 / QR 발급 | 운영진 | 승인+입금완료된 참가자에게 라벨 코드, 전원(참가+관람)에게 QR 토큰 발급. 이미 처리된 사람은 건드리지 않아 재실행 안전 |
  | 점수 시트 순서 반영 | 운영진 | 확정된 라벨 순서를 연동된 점수 시트에 일괄 전송 |
  | 참가자 CSV 백업 다운로드 | **운영진 전용**(`export_sensitive_data`) | 마스킹 없는 전체 데이터 백업 |
  | QR 발송용 명단 다운로드 | **운영진 전용** | 문자/카톡 대량발송 도구에 넣을 이름·연락처·QR 링크·안내문구 (이름은 본명만) |
  | 신청 확인용 명단 (엑셀) | 운영진 | 라벨 발급 전에도 사용 가능. 이름/연락처 마스킹, 미입금/학적 미승인 비고 표시 |
  | 공지용 명단 (엑셀) | 운영진 | 이름/연락처 마스킹, 장르별 탭, 확정 순서 포함 |
  | 점수표 (엑셀) | **운영진 전용** | 마스킹 없음, 장르별 탭, 스태프 현장 운용용 |

  참가자 CSV 백업을 제외한 나머지 다섯 액션(QR 발송용 명단, 신청 확인용
  명단, 공지용 명단, 점수표, 라벨/QR 발급 대상 산정)은 모두 환불
  (`payment_status=REFUND`)된 참가자를 명단에서 제외한다 — 취소된
  참가자에게 QR이 발송되거나 현장 명단에 남아있지 않도록 하기 위함. CSV
  백업만 예외로 환불자를 포함한 전체 데이터를 그대로 남긴다(감사/기록
  목적).

### 4.4 운영진 기능 — 참가자 관리 (Django Admin `Participants`)

- 목록: 이름/연락처/학교 검색, 회차·구분·학적검수·입금·체크인·장르
  필터, 상태별 뱃지 표시.
- 통계 타일: 기준 회차(필터 중인 회차 → 없으면 활성 회차 → 없으면 최신
  회차)의 총 신청/학적검수 대기(대기+반려 합산)/입금 대기/환불/체크인 완료
  5개. **"총 신청"만 환불 인원을 포함**하고(취소돼도 실제 신청이 있었던
  인원 수를 그대로 보여주려는 의도), 학적검수 대기·입금 대기·체크인
  완료·장르별 분포는 환불 인원을 제외한 "실제로 진행 중인" 인원 기준이다
  (체크인 완료 타일의 분모도 마찬가지).
- 장르별 참가자 패널: 장르별 인원 분포를 막대그래프로 표시(참가자만
  대상, 관람은 장르가 없어 집계에서 제외). 제목의 총원 숫자는 막대들의
  합과 항상 일치한다.
- 상세 편집: 기본 정보/신청 정보/검수/라벨/QR·체크인/기타 섹션. 검수
  섹션에는 학적검수 상태 옆에 자유 메모(`verification_note`, 반려 사유 등)를
  남길 수 있다 — 참가자에게는 노출되지 않는 운영진 전용 메모.
- 선택 액션:

  | 액션 | 설명 |
  | --- | --- |
  | 학적검수 승인 처리 | 선택한 참가자(참가 구분만)를 `APPROVED`로 |
  | 입금 확인 처리 | 선택한 참가자를 `PAID`로 |
  | 라벨 맞바꾸기 | 정확히 2명, 같은 회차·같은 장르 조건에서 라벨(조/번호) 상호 교환 |
  | 입금 완료 → 환불 처리 | `PAID`였던 사람만 `REFUND`로 전환하며, 이미 발급된 라벨/QR도 함께 회수(재발급 시 다시 대상이 되지 않도록) |

### 4.5 계정 관리 (슈퍼유저 전용)

- 계정 목록 대시보드 (`/admin/accounts/`): 스태프 이상 전체 계정을
  권한(슈퍼유저→운영진→스태프) 순으로, 활성/초대됨/비활성 상태와 함께 표시.
- 계정 상세 수정 (Django Admin `Users`): 이름/이메일, 권한(스태프/운영진/
  슈퍼유저 라디오 하나로 `is_staff`/`is_superuser`/"운영진" 그룹 조합을
  결정), 계정 활성화 토글, 비밀번호 재설정 이메일 발송(본인이 직접
  바꾸도록 유도 — 관리자가 비밀번호를 직접 입력하지 않음), 계정 삭제.
- 슈퍼유저만 슈퍼유저를 만들 수 있다(서버 측에서 재검증).

## 5. 외부 연동

### 5.1 구글 폼 신청 수집

`google-apps-script/Forwarder.gs`가 구글 폼 응답 시트의 신규 제출/백필을
`POST /api/import/google-form/`로 전달한다. 시트 행(외부 참조값) 단위로
멱등하게 처리되어, 같은 응답을 여러 번 보내도 중복 생성되지 않는다. 폼의
입금확인 체크 여부와 무관하게 항상 검수 대기(`PENDING`)로 들어온다. 참가
신청인데 장르가 비어있거나 `Genre` 선택지와 정확히 일치하지 않으면 그
행만 저장하지 않고 에러로 반환한다(시트 헤더 매핑이 틀어져 장르별 엑셀/
점수표 어디에도 안 잡히는 "유령 참가자"가 생기는 걸 막기 위함).

### 5.2 예비 신청 폼

구글 폼을 못 쓰는 경우를 위한 대체 경로(`/register/`). 별도 검수 과정
없이 활성 회차에 바로 `PENDING` 상태로 접수된다.

### 5.3 점수 시트 실시간 반영 (선택, 회차별 설정)

`google-apps-script/SheetSync.gs`를 인포/공연장 점수 시트에 배포하고 그
URL을 회차의 `sheet_sync_url`에 등록하면, Django → 시트 방향으로 두 가지가
반영된다.

- **도착 여부**: 체크인 확정 즉시 자동 반영(백그라운드 스레드, 실패해도
  체크인 자체는 막지 않고 로그만 남김).
- **순서(라벨 코드)**: 자동 아님 — "점수 시트 순서 반영" 액션을 눌러야
  일괄 반영.

## 6. 핵심 비즈니스 규칙

- 활성 회차는 항상 최대 1개(모델 `save()`에서 자동 강제).
- 라벨 배정: 장르별로 그룹 크기 10명 단위, 동명이인은 가능한 한 다른
  그룹으로 분리, 기존에 이미 배정된 사람은 유지, 승인+입금완료된 사람만
  신규 배정 대상, 몇 번을 재실행해도 안전(멱등) — `assign_labels_and_tokens`
  / `label_assign.py`.
- QR 토큰 발급 조건: 입금 완료 AND (관람이거나 학적검수 승인).
- 체크인은 중복 처리되지 않는다(이미 `CHECKED_IN`이면 시각을 덮어쓰지
  않음). 같은 참가자를 거의 동시에 두 번 요청해도(붐비는 입구에서 스태프
  두 명이 같은 QR을 동시에 스캔하는 경우 등) DB 행 잠금(`select_for_update`,
  운영 DB인 Postgres 기준)으로 중복 처리를 막는다.
- 환불 처리 시 발급된 라벨/QR을 함께 회수해, 환불자가 기존 QR로 재입장
  체크인되지 않도록 한다. 환불된 참가자는 "총 신청" 타일과 CSV 백업에는
  계속 잡히지만(취소돼도 신청 이력 자체는 남겨야 하므로), 그 외 통계
  타일·장르 분포·모든 명단/엑셀 내보내기에서는 제외된다.
- 이름은 "본명/댄서명" 형식을 전제로 하며, 구분자(`/`) 앞뒤 공백은 무시하고
  파싱한다(내부 공백은 보존) — 마스킹·QR 발송 명단의 실명 추출에 공통 적용.

## 7. 범위 밖 (의도적으로 제외)

- 학적증명서 OCR 자동 대조
- 문자/카카오 알림톡 자동 발송 (현재는 명단만 뽑아 수동 발송)
- 세분화된 역할 권한 (현재는 스태프/운영진/슈퍼유저 3단계까지만 지원)
